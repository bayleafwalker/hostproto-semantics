HostProtoProject summary28 Aug 2026

Typed, evidence-bearing interaction with stateful hosts

A browser context, a debug session, an interactive process: hosts you must observe before you act, where the act changes the next observation, and where a reference you hold may already be stale. HostProto is the small set of semantics that makes an agent's work on such hosts checkable after the fact.

The pointWhy this exists

Agents act on hosts. Nobody can currently prove what they did.

MCP gives an agent tools. A2A lets agents delegate work to each other. Neither says what it means to click something that has since moved, to read a page that has since navigated, or to claim an effect that nobody observed. Every host adapter reinvents those rules privately, and the evidence an agent leaves behind is whatever it felt like logging.

HostProto's claim is that nine semantics cover every stateful host, without becoming host-specific: opaque expiring handles; revisioned observations with a cursor into an ordered event stream; target references scoped to a revision and rejected before the host is touched when it has moved; declared preconditions; declared intent; receipts that separate attempted, accepted, executed and verified; content-addressed evidence; capability profiles earned by execution, never by declaration; and recovery as named states rather than exceptions.

It is deliberately not a third wire protocol. MCP carries the primitives, A2A carries delegated work, HostProto is the semantics both carry — canonical JSON Schemas used verbatim as MCP tool schemas and as an A2A profile extension. Adding a scheduler, a task store, a transport, or a universal Task type to HostProto is defined as failure.

MCP owns

Discoverable tools with typed schemas, structured results, resources and subscriptions, server-minted handles, elicitation.

A2A owns

Agent discovery, coarse skills, delegated tasks, streaming, interruption, artifacts.

HostProto owns

Handles, revision and freshness, target identity and invalidation, preconditions, intent, receipts, evidence, capability truth, recovery.

The domain runtime owns

Execution lifecycle: claims, retries, cancellation, terminality. Correlated with MCP and A2A tasks, never merged.

The semantics were first executed under browser names in browser-workbench: a frozen twelve-scenario corpus run on a deterministic mock, then on a real embedded WebKitGTK engine (twelve scenarios × three repetitions × two profile variants, byte-deterministic), then cross-checked against Playwright/WebKit as an external oracle. Six of twelve scenarios can be posed to the oracle; all six are equivalent, and the other six name the host mechanism the oracle lacks. That milestone is now frozen.

The generalization lives in three new repositories. hostproto-semantics holds the schemas, the alignment maps from both prior projects, the plan, and the kill gates — nothing runnable. hostproto-mcp-playwright is the reference adapter: a headless Chromium exposed through MCP 2026-07-28, whose tool schemas are the pinned bundles verbatim and whose every result is validated against them before it leaves the process. hostproto-a2a-worker is the A2A 1.0 host-worker: one Agent Card, one skill, each task projected from a domain run that drives the adapter through many MCP calls.

How it's being doneMethod

Every claim has a denominator, and every verification is earned.

The working rule across all three repositories: no quiet denominator shrinkage. A scenario is passed, failed, blocked, or inapplicable, and a report always lists all twelve. Suppressions in a comparison are declared and echoed into the evidence. A capability is runtime-verified only by an operation that completed in a passed run — the mock backend earns it the same way the real engine does.

The adapter never copies a schema. It pins a commit of the semantics repository and a SHA-256 per bundle, verifies on fetch and again on load, and refuses a mismatch. There are no hand-written TypeScript interfaces for HostProto types. Tests are wire-level: a real client pinned to 2026-07-28, a real stdio server, a real browser, a loopback fixture.

What the wire taught us that no changelog said

  • On the 2026-07-28 era resources/subscribe no longer exists; a resource subscription is a URI array in the subscriptions/listen filter.
  • server/discover returns supportedVersions; server identity rides _meta on every result.
  • MCP defines no handle concept — its stateful-tools guidance is non-normative. HostProto's handles schema is needed, not duplicated.
  • A gate reporting blocked is also where an infrastructure defect hides if nobody reads the reason. One had, since slice 5.

Kill gates

The generalization stops if any of these becomes true:

  1. browser and debugger need different core envelopes;
  2. the shared schema degenerates into arbitrary JSON;
  3. HostProto acquires a scheduler, durable task store, or transport;
  4. individual clicks or debugger steps become A2A skills;
  5. every MCP call gets wrapped in an A2A task;
  6. adapter-specific escape hatches become normal;
  7. observation revision cannot be expressed uniformly across hosts;
  8. runtime verification stops being earnable per adapter.

Gates 2 and 6 were tested by step 2 and did not fire. Gates 1, 7 and 8 were tested by the DAP spike in step 3 and did not fire either. Gates 3, 4 and 5 were tested by the A2A worker in step 4: the run store stayed the worker's, one skill covered many primitives, one task covered many MCP calls. What remains is the debugger runtime: a spike proves the schemas can describe a debugger; only an adapter proves it can honour them.
